### CheckRide Scoring
- ~~**Diversion handling (engine failure / alternate landing)**~~ — **shipped 2026-08-13** (spec'd 2026-08-12). Engine-out/fire no longer cost points (`Once("Engine Fire"/"Engine Out", ..., 0)` — kept as 0-pt breakdown lines, not dropped), and landing away from the planned destination after a declared diversion logs `DivertedToAlternate` instead of `WrongArrivalAirport`, waiving that penalty too. Two ways to declare a diversion, both landing in the same place:
  - **Automatic** — `DeclareDiversion()` fires the instant `_eng1OutFlagged`/`_eng2OutFlagged`/`_engineFireFlagged` first flips (`FlightMonitor.cs`, in `DetectFailures`), plus the one-shot `CalloutEngineFailure` voice callout (`sounds/engine_failure/`, folder created by Brian, wired in `FlightListForm.cs`).
  - **Manual** — new "Diverting to alternate airport" checkbox in the client's flight-in-progress status bar (`FlightListForm.cs`, `_chkDivert`), visible only while `AppState.Recording`. Checking it calls `FlightMonitor.DeclarePilotDiversion()` — same landing-time effect, no voice callout (a deliberate UI action doesn't need an instructor line telling the pilot there's trouble). Locks (disables) once checked; resets each new flight.
  - Both paths are a one-way latch (`_diversionDeclared`) logged as a new `FlightEventType.DiversionDeclared` milestone at declaration time, timestamped separately from the eventual `DivertedToAlternate` at landing — report timeline reads as failure/declaration → landing.
  - **`checkride_results.notes` column added** (migration `20260813000000_add_checkride_notes.sql`, applied directly to the linked Supabase project) — populated with a plain-language message plus raw landing GPS coords (`snap.Latitude`/`snap.Longitude`) when a diversion lands away from plan. Deliberately does **not** touch `saved_flights.arr_id`/`arr_name` (shared flight-plan row, confirmed one route can back 7+ separate attempts) and deliberately does **not** resolve coords to an airport ICAO (would need to parse the embedded 19MB `refdata/airports.json`, which nothing in the C# client currently does) — that's a pure future display upgrade, not blocking.
  - **report.html**: both `BAD` event-color Sets (map + chart) gained `DiversionDeclared` (red — still a notable emergency moment) but *not* `DivertedToAlternate` (left yellow/neutral — it's the good outcome, not a mistake). The map's end-of-track dot gained a third amber state (`wasDiverted`) distinct from red (crash/wrong-airport) and white/green (arrived as planned). `endedShortOfDest` now also includes `DivertedToAlternate` so the planned-arrival ICAO label doesn't get misapplied to a diversion's actual landing point. `notes` rendered under the score/date line on the hero, and added to the Supabase `select()` column list (was missing it initially — would've silently never fetched despite the grant).
  - Scoring version bumped to `xp12-1.20`.
  - **Follow-up, not done**: airport-name resolution for the note (v2, per above), and a nearest-suitable-airport-based bonus for a good diversion decision (dropped from scope — final design converged on "no penalty," not "bonus," see conversation 2026-08-12/13).
- **3+ engine monitoring gap** — noticed 2026-08-13 while wiring the diversion feature. `XP12Connector.cs` only polls `sim/flightmodel/engine/ENGN_running` at index 0 and 1 (`eng1Task`/`eng2Task`), and `FlightDataSnapshot` only has `Engine1Running`/`Engine2Running`. This is pre-existing and affects the *whole* engine-out detection system, not just the new diversion trigger: for a 1-engine aircraft it's fine (engine 2 never starts, so its checks simply never fire), but for anything with 3+ engines (747, C-130, etc.), losing engine 3 or 4 produces **zero detection** — no `FailureEngineOut` event, no diversion trigger, nothing. Every aircraft flown so far (King Air 350, ERJ 145, A319, Skyhawk) is 1-2 engines, so this hasn't bitten anyone yet. Fix needs new datarefs (`ENGN_running` index 2, 3...), new `FlightDataSnapshot` fields, and generalizing `DetectFailures`'s engine-out loop to N engines instead of two hardcoded checks.
- **Badge system for scoring bonuses** — currently bonuses (Greaser Landing, Smooth Landing, Clean Systems, Clean Flight, Hand Flown, Night Flight, IMC Flight, Crosswind Landing, Rain Landing, Low Visibility Landing) only show as point line items in the score breakdown. Turn them into collectible badges/achievements shown on the flight report and aggregated on a user profile (e.g. "5x Greaser Landings", "First IMC Flight"). Needs: badge icon set, a badges table or derived-from-breakdown aggregation, UI on report.html and a My Stats-style page.
- **TEST NEEDED: flex/derated-thrust jet takeoff vs N1 low-power check** — piston aircraft confirmed fine (see Recently Shipped), but real jets commonly use flex/assumed-temperature reduced-thrust takeoffs legitimately below 90% N1 — could still false-flag a normal airline-style takeoff. Need to fly a jet (and ideally a turboprop) and check the logged liftoff N1% before trusting this check universally. May need to gate using the FAA `Physical_Class_Engine` data already loaded in `AircraftDb`.
- ~~**Real turbulence callout, wired to an actual dataref**~~ — **re-retired 2026-08-13.** Two signals tried, both failed once used for real (region-forecast dataref, then rolling-stddev-of-Gn); not worth a third attempt without a per-tick physics dataref for airframe buffeting, which XP12's Web API doesn't currently expose. Removed `CalloutTurbulence`, the Gn-window detection block, and the `FlightListForm.cs` subscription — same shape as the original 2026-07-14 removal. `FlightEventType.Turbulence` kept in the enum only so old event logs still deserialize; report.html's Pax Comfort derivation still filters on it but will simply never match going forward. History below, kept for the full "why we tried, why it failed" record.
  - the "Turbulence" callout was removed (2026-07-14) after live-flight testing showed it was firing once on IMC entry (`clouds = turbulence in practice`, a proxy that was never accurate) and, worse, G-force data over a genuinely rough 5-minute stretch of a real flight showed *zero* variance (Gn sat in a flat 0.94-1.05 band despite the pilot feeling turbulence with 51% rain) — confirming G-force isn't a usable signal either at 1Hz.
  - **2026-07-19 update:** `sim/weather/region/turbulence` confirmed live via the Web API mid-flight (King Air 350, FL280, XP12 12.4.3) — it resolves (`float_array`, id session-local) and is a **13-element altitude-banded array**, not 3 elements as previously assumed (same 13-level layout as `sim/weather/aircraft/wind_altitude_msl_m`/`wind_speed_kts`, indices `[0]`=surface…`[12]`≈16,179m MSL — not yet confirmed the turbulence array uses the *same* altitude bands, just the same element count).
    - Reading while pilot reported **bumpy**: `[0.0195, 0.0199, 0.0216, 0.0229, 0.0231, 0.0219, 0.0208, 0.0200, 0.0190, 0.0163, 0.0148, 0.0137, 0.0]`
    - Reading ~2.5 min later while pilot reported **smooth**: `[0.0192, 0.0192, 0.0216, 0.0230, 0.0235, 0.0215, 0.0200, 0.0195, 0.0181, 0.0157, 0.0143, 0.0128, 0.0]`
    - **These two readings are nearly identical** despite the subjective bumpy→smooth change — a discouraging early signal that this may be the same failure mode as the cloud-based proxy: a slow-moving regional weather-model forecast (it lives under `sim/weather/region/*`, same namespace as `cloud_base_msl_m`/`cloud_coverage_percent`) rather than a live per-tick physics reading of actual felt buffeting at the aircraft's position.
    - **Third reading ~14 min later, pilot reported MORE bouncing:** `[0.0172, 0.0180, 0.0191, 0.0190, 0.0181, 0.0174, 0.0173, 0.0176, 0.0171, 0.0166, 0.0153, 0.0155, 0.0]` — these values are **lower** than both prior readings, i.e. moved the *wrong direction* relative to what the pilot actually felt. `Gn` was flat again too (0.98–1.04). This is a clear negative result, not just inconclusive — the dataref appears uncorrelated (or anti-correlated) with real felt turbulence.
    - **Conclusion: `sim/weather/region/turbulence` is very likely the same dead end as the cloud-based proxy** — a slow-moving regional forecast value, not a live felt-turbulence signal. Not worth wiring into `FlightMonitor.cs` as-is. The turbulence callout should stay retired until XP12's Web API exposes something more direct (there is currently no known per-tick physics dataref for airframe buffeting/gust response — both candidates tried so far, clouds and this, have failed the same way).
  - **2026-07-21 update — reversed the conclusion, shipped a fix: rolling *stddev* of Gn (not the raw instantaneous value) is a usable signal.** Live King Air 350 flight, FL325, cruise, real weather: instantaneous Gn still looked flat tick-to-tick (matches the earlier negative finding), but stddev of Gn over a rolling 20s window told a completely different story:
    - Calm baseline throughout the flight (multiple altitudes/phases): stddev **~0.02–0.04**
    - Pilot-reported **"real rough right now"** (t≈4918-4942s, FL325, 67-71% snow): stddev **0.126**
    - Earlier pilot-reported **"heavy turbulence"** (t≈4384-4444s, rain climbing 71→81%): stddev **0.13–0.18**
    - Pilot-reported **"just settled down"** immediately after: stddev dropped straight back to **~0.02–0.03**
    - This is a clean, repeatable, well-correlated pattern — turbulent stretches are consistently ~4-8x the calm baseline, confirmed against three independent pilot reports in the same flight (rough → smooth → rough again). This looks like a genuine turbulence signature, not noise.
    - **Shipped:** `CalloutTurbulence` event in `FlightMonitor.cs`, Schmitt-trigger hysteresis on the rolling stddev (trip >`TurbulenceGnStdDevTripThreshold`=0.09, re-arm <`TurbulenceGnStdDevResetThreshold`=0.05, 20s window via `TurbulenceGnWindowSize`), wired to the previously-unused `callout_turbulence` sound folder. Passenger-comfort callout only, no scoring penalty. Not yet flight-tested with the actual audio (build was pending an app restart to release the file lock) — thresholds are calibrated off this one flight's data and should be sanity-checked across a few more flights/aircraft before considering this fully validated.
  - **2026-08-11 update — regression report: still misfiring, this time on smooth/normal flying, not just IMC entry.** The 2026-07-21 rolling-stddev fix was validated against one flight's data; live use since then shows it firing during ordinary flying with no actual turbulence, so the trip threshold (or the whole stddev-of-Gn approach) isn't holding up outside that one dataset. Given this is the *second* signal (after the region-forecast dataref and the raw-Gn dead ends above) to fail once used for real, worth considering just pulling `CalloutTurbulence` back out again rather than continuing to chase thresholds — re-retire until there's a per-tick physics dataref for airframe buffeting, or accept it as a lower-value nice-to-have and tune thresholds looser (fewer false positives, likely fewer true positives too) instead of fully removing.
- **Voice callout for 250kt/10,000ft speed limit violation** — `FlightEventType.SpeedLimitViolation` (FAR 91.117) already scores a penalty (`PenaltySpeedLimit`) but has no voice callout, unlike Overspeed/HighBank which do (`CalloutOverspeed`, `CalloutHighBank`). Confirmed via live test flight (twin turboprop climbed to 250kt below 10k without any audible warning — pilot didn't realize until reviewing the log). Add a callout event mirroring the existing pattern. Unclear yet whether the current point penalty is calibrated right — revisit after the callout's in and more real flights hit it.
