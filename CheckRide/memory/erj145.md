# X-Crafts ERJ 145 — CheckRide findings (2026-08-22)

First real flight on this airframe (`checkride_ef5e2bdf_20260822_150459`). Confirmed live via
XP12 Web API while the flight was in progress (on ground, engines running, KCLT).
`sim/aircraft/view/acf_ui_name` = `"X-Crafts ERJ 145"`. All 68 of CheckRide's existing datarefs
resolved fine on this addon (`ID resolution: 68/68 resolved`) — unlike the King Air 350, this
addon doesn't need a custom-namespace workaround for the core tick-log fields.

## Bug found: wrong V-speeds applied to this flight

The session log shows:
```
Aircraft: X-Crafts ERJ 145
Aircraft limits — using verified POH V-speeds (Beechcraft King Air 350 POH — Vmo 263 KIAS...)
Aircraft limits — Vso=81kt Vno=263kt Vne=263kt Vfe=202kt Vs=139kt → Vref=105kt
```
CheckRide applied the **King Air 350** POH override to an ERJ 145 flight. Root cause
(`FlightListForm.cs` ~L425, `AircraftVSpeeds.Find`, `FlightMonitor.cs` L408): the app
auto-restores the last aircraft ICAO the user picked from a server-persisted preference
(`GetLastAircraftIcaoAsync`) whenever the in-session dropdown hasn't been touched. The user's
last flight was in the King Air 350, so that stale pick silently won over the live
`acf_ui_name`, and `aircraft.json` has no ERJ 145 entry anyway (only King Air 350, Cessna
172SP, Baron 58, Citation X, Cirrus SR22, Cirrus Vision SF50, Lancair Evolution).

**Impact:** real ERJ 145 limits (see below) are Vno/Vne=250, Vfe=230, Vso=121, Vs=139 — all
sane numbers the addon itself reports correctly. The King Air override made scoring
~13kt *too lenient* on overspeed (263 vs 250) and ~28kt *too strict* on flap overspeed
(202 vs 230). Nothing to fix mid-flight; just don't trust this flight's overspeed/flap-speed
grading. Fix for later: `AircraftVSpeeds.Find` (or its caller) should refuse to reuse a
remembered ICAO pick when it doesn't match the live `acf_ui_name` at all, rather than
trusting it silently. See [[checkride-status]] TODO list.

## Live-confirmed V-speeds (best source found — use these, not a static POH table)

The addon's own FMS computes real per-flight V-speeds from loaded weight/config and exposes
them directly — better than any hardcoded override:
- `XCrafts/ERJ/FMS/ACARS_vspeed_data_V1` = 116 (matches `XCrafts/ERJ/MFD/vspeeds/V1`)
- `XCrafts/ERJ/FMS/ACARS_vspeed_data_VR` = 117
- `XCrafts/ERJ/FMS/ACARS_vspeed_data_V2` = 129
- `XCrafts/ERJ/FMS/ACARS_vspeed_data_Vapp` = 160
- `XCrafts/ERJ/FMS/ACARS_vspeed_data_Vref` = 0 (not yet computed — no approach loaded yet at poll time)
- `XCrafts/ERJ/FMS/ACARS_takeoff_ready` / `ACARS_landing_ready` — bool, FMS-side readiness flags

Also `XCrafts/ERJ/MFD/vspeeds/{V1,V2,VR}` mirror the ACARS values (didn't check for a
`Vref`/`Vapp` MFD twin).

Stock airframe limits (`sim/aircraft/view/acf_*`) are all sane on this addon, unlike the King
Air's mislabeled `acf_Vno`:
- `acf_Vso` = 121, `acf_Vs` = 139, `acf_Vno` = 250, `acf_Vne` = 250, `acf_Vfe` = 230
- `sim/aircraft/controls/acf_flap_detents` = 3

## FMS route/distance — this addon DOES sync stock datarefs (unlike King Air 350)

Confirmed live and populated (King Air 350's addon leaves these at 0 — see
[[checkride-status]]):
- `sim/cockpit2/radios/indicators/fms_distance_to_tod_pilot` = 192.0 (nm to top of descent)
- `sim/cockpit2/radios/indicators/gps_dme_distance_nm` = 0.96
Worth wiring the route-progress/distance-remaining idea (`CheckRide_Voice_System_Plan.md`)
against these stock paths for this airframe rather than needing an addon-specific fallback.

## Other jet-relevant data confirmed live and worth adding

- **Reverser status:** `sim/flightmodel2/engines/thrust_reverser_deploy_ratio` reads
  denormalized near-zero garbage (`2.24e-44`) on this addon at idle — don't use it. Use the
  boolean `sim/cockpit2/annunciators/reverser_deployed` (read 0, clean) or `reverser_on` /
  `reverser_not_ready` instead. Jet equivalent of the King Air's `prop_in_beta` disambiguation
  for `throttle_ratio`.
- **Fuel flow per engine:** `sim/cockpit2/engine/indicators/fuel_flow_kg_sec` populated
  correctly (`[0.334, 0.334, 0, 0, ...]` at idle) — not currently logged; only total fuel
  (`m_fuel_total`) is.
- **Cabin pressurization:** `sim/cockpit/pressure/cabin_altitude_actual_ft` (330ft) and
  `cabin_pressure_differential_psi` (2.77) both populated — could support a rapid-decompression
  or pressurization-fault check that wouldn't apply to unpressurized GA singles.
  `bleed_air_on`/`bleed_air_mode` and `sim/cockpit2/bleedair/actuators/pack_left/center/right`
  (read `1` = on) also populated.
- **APU:** `sim/aircraft/electrical/bus_apu_is_on` = 2 (on/generating) — populated.
- **Autothrottle:** stock `sim/cockpit2/autopilot/autothrottle_enabled` = **-1** (X-Plane's
  sentinel for "not modeled on this airframe") and `autothrottle_on` = 0. No
  `XCrafts/ERJ/*athr*` or `*autothrottle*` custom dataref found either — inconclusive whether
  this addon models A/T at all; didn't test engaging it live. Don't build an autothrottle
  check on this airframe until that's confirmed one way or the other.
- **Gear-per-wheel contact is unreliable on this addon too:** `sim/flightmodel2/gear/on_ground`
  read `[0,0,0,...]` (all off-ground) while the aircraft was stationary on the ramp with
  engines running. Same family of issue as the King Air's nose-gear-only quirk — don't trust
  this array for ground/liftoff detection on this airframe either; CheckRide already keys phase
  transitions off `y_agl`/groundspeed instead of `on_ground`, which is the right call and
  sidesteps this.
- **ITT naming holds up:** the addon itself labels its engine temp `XCrafts/ERJ/engines/eng1_itt`
  /`eng2_itt` (289°C at idle, matches the stock `ITT_deg_C` CheckRide already logs) — so despite
  this being a turbofan, "ITT" isn't a mislabel for this specific airframe. Not a generic rule
  for all jets, just confirmed fine here.
- **Discrete flap position:** `XCrafts/ERJ/flap_lever_ratio` (0.333 at detent 1 of 3) exists
  alongside the stock continuous `sim/flightmodel/controls/flaprat` (0.20) CheckRide already
  reads — the two don't move in lockstep 1:1 (lever ratio is detent-quantized, flaprat is the
  animated surface position), so if a discrete "which flap detent" reading is ever wanted,
  `flap_lever_ratio` + `acf_flap_detents` is the pair to use, not `flaprat` alone.
